# Buildpack startup comparison

This owned harness compares the four independent application images. It uses Python's standard library and the Docker Engine API through the mounted socket; no Docker CLI or Java is needed inside the helper image. `make bench` selects one application, while `make compare` builds and measures all four.

Each repetition creates a new container with one CPU and 512 MiB memory. Timing begins immediately before the Docker start request; image builds/pulls and container creation happen outside that window. The harness verifies readiness and AOT mode, captures the first quote response, samples memory, and checks product, quote, computation, metadata and input-error responses. A wrong response fails the report. Warmups are separate fresh containers, and measured mode order is shuffled with seed 42. Every container has a unique ID and is removed in a `finally` block; the harness does not stop applications launched by `make test-app`.

Reported startup is elapsed time through verified readiness, including container-start/API overhead, CNB launcher execution and 20 ms readiness polling. First quote is cumulative from that same start request. Memory is Docker container working set (usage minus inactive file pages), sampled just after the first quote; it is not Java heap size or process RSS. CPU time covers all processes in the container through that sample. Default OS page cache remains enabled. p95 uses linear interpolation and is descriptive with the default ten samples.

Each report folder contains only `report.html` plus `artifacts/`. Supporting files include `summary.json`, `environment.json`, `runs.csv`, `runs.jsonl`, per-container application logs and the most recent build logs/costs when available. Image IDs, architecture, sizes and buildpack metadata are recorded. Build costs include the full `pack` invocation (downloads, tests, cache/native preparation and export) and may reuse caches. They are distinct from measured startup. Failed runs produce `artifacts/failure.json` and return nonzero. Reports are ignored by Git.

This comparison measures local container startup. It does not measure steady-state load, cluster scheduling, image-pull latency or native compiler peak memory. Buildpack runtime versions and collectors can differ, and results must not be directly mixed with process-only measurements from other projects.
